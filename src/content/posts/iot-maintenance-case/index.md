园区的一台循环泵出现运行异常提示。平台能展示趋势，但维修人员还需要知道它当时处于什么工况，是否影响服务，什么时候允许检修，以及恢复以后怎样确认问题解决。

**本文是一份虚构的流程教学案例，不是故障诊断指南。** 不给出真实设备的报警阈值、检修操作或保护参数；具体判断和现场操作由具备相应职责的人员按设备与运行要求开展。

## 1. 目标：让发现、接手和复核接得起来

假设过去主要依靠巡查和电话报修，故障信息分散，换班以后经常需要重新询问。

项目第一阶段不追求预测所有故障，而是做到：发现线索时知道影响对象，接手人员能找到证据，处理完成后能够复核，并为后续分析留下记录。

| 角色 | 在案例中的职责 |
| --- | --- |
| 运行人员 | 确认工况、服务影响和可用检修窗口 |
| 维护人员 | 核查设备、实施经安排的检修 |
| 复核人员 | 按完成条件检查恢复情况 |
| 系统维护人员 | 保证采集、告警和记录链路可用 |

## 2. 准备设备与业务背景

为泵 P-01 建立资产、安装位置、服务范围、相关测点和维护记录。状态数据可以包括设备实际支持的运行反馈、电气量及相应测量信息。

每项数据都需要说明测量位置、单位、时间和质量。当前运行模式、计划停机和检修状态，也需要有明确来源。

```text
设备 P-01
   ├── 测点及有效性
   ├── 当前工况与运行安排
   ├── 服务对象与影响范围
   └── 检修历史与责任人员
```

没有这些背景，同一条“数值升高”提醒，可能被不同人员理解成不同问题。

## 3. 定义的是核查规则，不是自动诊断结论

假设现场专业人员确认了一组适用于该设备的判断条件。平台只在设备处于对应运行模式、数据有效且条件持续满足时，形成待核查告警。

规则记录包含适用设备、版本、触发依据、恢复条件和失去数据时的处理方式。

如果数据中断，应表达“判断依据不足”或相应数据异常，而不是认为原运行异常已经消失。如果设备进入计划检修，则按约定调整通知，并保留相关状态。

## 4. 走一遍事件时间线

下面是人为构造的流程记录，仅用于说明各时间点的含义：

| 时间 | 事件 | 可以确认什么 |
| --- | --- | --- |
| 09:10 | 满足核查规则，形成告警 | 出现需要关注的线索 |
| 09:12 | 值班人员确认接手 | 工作已有负责人 |
| 09:20 | 核对工况，决定现场检查 | 已完成初步判断 |
| 09:40 | 完成运行协调，允许检修准备 | 具备约定工作条件 |
| 10:25 | 维护人员提交处理记录 | 已执行记录中的措施 |
| 10:40 | 按要求完成复核 | 满足本次恢复判据 |

通知发出不等于 09:12 的接手，10:25 的提交也不等于 10:40 的复核。分开记录，才能知道时间花在了哪里。

## 5. 现场检查可能走向不同结果

### 5.1 数据或传感器有问题

维护人员可能发现采集配置错误、测点失效或其他数据问题。此时应修复数据链路，并说明本次告警并未确认机械故障。

必要时对受影响的历史记录加说明，而不是继续用它们训练“故障识别”模型。

### 5.2 工况变化可以解释现象

若数据反映了合理的运行变化，就记录工况与核查依据，并检查规则是否需要调整适用条件。

不能为了减少告警直接大幅放宽阈值，因为这样可能掩盖其他工况下的真实问题。

### 5.3 确认需要检修

在本案例的一条假设分支中，专业人员确认存在需要处理的设备问题，并按现场程序完成检修。

平台记录实际原因、措施、相关部件与人员，但不要求系统凭曲线自行推断具体故障。证据不足时，应允许写明尚未确定的部分。

## 6. 复核要同时看设备与服务

复核可以包括设备反馈、相关测量、运行观察和服务状态，具体判据由现场要求确定。

```text
检修措施已完成
       ↓
检查设备状态与必要试运行结果
       ↓
确认对应服务恢复
       ↓
核对未解决事项，关闭或转交任务
```

如果设备短暂恢复后再次异常，应能关联原任务，判断是否复发，而不是每次都当成毫无关系的新问题。

如果暂时没有条件复核，可以保持“等待复核”，说明原因和下一步。不能以停止上报告警代替实际恢复证据。

## 7. 这一次事件，能计算什么指标？

按示例时间线，从发现到接手是 2 分钟，从发现到复核是 90 分钟。

这两个数分别描述不同工作环节，不能直接称为设备停机时长。设备何时停止、是否有备用能力维持服务，以及何时恢复，都需要另外的事实记录。

同时，一次事件不能证明整体维护效率改善。需要在一致口径下观察多次事件，并考虑故障类型、检修条件与人员安排。

可以持续评价有效提醒、误报、漏报线索、接手与复核时间、重复故障和维护工作量。对没有被系统发现而由人工发现的问题，也应回填，避免评价只看到成功样本。

## 8. 异常流程如何验收？

| 场景 | 要检查的行为 |
| --- | --- |
| 同一问题重复触发 | 维护同一实例及历史，避免重复派单 |
| 网关离线影响多个测点 | 提示关联核查，不直接认定多台设备损坏 |
| 接手人员换班 | 有明确交接与新责任人 |
| 工单转派无人接受 | 保留责任并按规则升级 |
| 维护提交后数据仍异常 | 等待复核或继续处理，不盲目关单 |
| 复核后再次发生 | 能关联历史，支持复发分析 |

这些可以先用模拟事件验证软件流程，再结合现场工作演练，确保系统状态与人员理解一致。

## 9. 用三个问题复盘这个案例

**规则触发，是否说明已经知道故障原因？**

不是。它提供核查线索，原因需要相应证据。

**从发现到复核用了 90 分钟，是否意味着设备停了 90 分钟？**

不能这样推断。工作过程时长与设备停机、服务中断各有口径。

**工单写了“已修复”，为什么还要复核？**

因为执行措施与达到恢复判据是不同事实。
