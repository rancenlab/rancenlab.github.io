前面的文章分别介绍了采集、设备管理、数据处理和业务闭环。这次把它们放进同一个项目：一个小园区希望减少人工抄表，并查清办公楼夜间为什么仍有较高用电。

**本文是虚构的教学案例。设备数量、时间和读数用于解释方法，不是实际项目数据或节能承诺。** 案例先做到可靠监测和人员核查，再在授权范围内调整运行安排。

## 1. 场景与目标：先把“节能”拆成可开展的工作

假设园区有 A、B 两栋办公楼，每栋设总电表，A 栋还具有一组办公空调分项计量。过去由设施人员定期抄表，异常主要靠月底报表和现场反馈发现。

第一阶段确定两个目标：减少抄表和核对的重复工作；识别值得检查的夜间空调用电，并留下完整处理记录。

不直接承诺某个节能比例，因为目前还没有足够证据确定原因和改善空间。

| 角色 | 负责什么 |
| --- | --- |
| 设施主管 | 确定使用安排、调整权限与验收口径 |
| 值班人员 | 接手提醒、核查临时使用情况 |
| 设备维护人员 | 核对仪表、采集与现场设备 |
| 系统实施人员 | 接入、数据解释、告警与记录流程 |

## 2. 先核对计量关系，再连接设备

需要确认 A 栋总表与空调分表分别计量哪些回路。总表已经包含分表对应负荷，两者不能再次相加当作整栋楼总量。

设备台账记录实物身份、型号、通信配置与计量范围；业务台账记录楼栋和使用区域；两者通过有生效时间的关系连接。

```text
A 栋总进线计量 ← A 栋总电表
       └── 空调分项计量 ← 空调分表

B 栋总进线计量 ← B 栋总电表
```

这张图表达计量关系，不是电气接线方案。现场仍需核实是否存在其他未覆盖或特殊计量情况。

验收时，选择可核对的读数检查单位、倍率、累计方向和时间。不要只因为平台能显示数字，就结束接入验收。

## 3. 建立数据链路，并明确故障后的行为

在这个案例中，网关读取电表，完成设备身份关联与解析，再把记录送到平台。

```text
电表 → 网关采集与缓存 → 平台校验和保存
                              ↓
                 历史查询、区间统计、核查提醒
                              ↓
                       人员处理与复核
```

为了教学，假设按分钟采集，具体周期在真实项目中应按设备能力和业务用途确定。

每条记录包含设备、测量项、值、单位、采集时间、接收时间与质量状态。断网时按已验证能力缓存，恢复后保留原采集时间补发；平台识别重复，避免旧记录覆盖新状态。

无效记录不转换成零。页面同时显示最近有效时间，让值班人员知道当前看到的是新数据还是旧记录。

## 4. 用一组数据发现值得核查的时段

假设 A 栋空调分表出现下面的有效累计读数：

| 时刻 | 累计电量 |
| --- | --- |
| 22:00 | 4,200 kWh |
| 次日 06:00 | 4,248 kWh |

在计量口径一致、没有换表或复位的假设下，这八小时用了：

```text
4,248 − 4,200 = 48 kWh
```

这只能说明该计量边界在该时段消耗了 48 度电，还不能直接认定全部是浪费。

平台继续关联使用计划：当晚这个区域没有计划使用，设备状态也显示部分空调仍运行。因此生成“非计划时段运行待核查”的提醒，而不是自动下发关闭命令。

## 5. 核查与调整：把例外放进流程

值班人员确认，当晚没有临时活动；设施人员进一步检查，发现一次加班后运行计划未恢复。

于是安排有权限的人员修正计划，记录适用区域、版本、生效时间和原因。随后核对设备实际生效状态，并向使用方确认没有遗漏必要需求。

如果查到的是临时加班，则记录有效例外和结束时间，不把这次运行简单当成故障。

```text
提醒 → 人员接手 → 核查使用安排
                    ├── 合理例外：记录并结束核查
                    └── 需要调整：授权操作 → 状态核验 → 后续观察
```

## 6. 效果核验：把观察值与归因分开

假设调整后的一个相同长度夜间区间，分表读数从 4,300 kWh 增至 4,316 kWh，对应 16 kWh。

两个区间的观察差值是 32 kWh。但不能立刻称为“系统节约了 32 kWh”，因为天气、使用情况和其他运行条件可能不同。

第一阶段可以先确认三件事：运行计划确实按预期生效；非计划运行减少；使用需求没有因此受到不合适影响。

进一步评价能耗改善时，应在事先约定的观察期内，记录天气、工作日、使用时间等条件，说明比较方法与无法解释的变化。若缺少足够证据，就报告观察结果，不强行给出节能比例。

## 7. 把异常分支也列入验收

| 情况 | 预期处理 |
| --- | --- |
| 网关断网后补发 | 历史记录归入原时段，不重复计算 |
| 区间边界读数缺失 | 标记统计不完整或按说明处理，不默认补零 |
| 设备更换 | 记录关系与初末读数，分段计算 |
| 临时使用 | 允许核查后记录例外，不强行关闭 |
| 计划下发但反馈丢失 | 保留待确认，查询状态后再判断 |
| 连续误报 | 回查数据、使用计划与规则，记录修订 |

模拟数据和隔离测试可以先验证软件处理，再按现场安排完成必要核验。控制动作和断电测试不能直接在正常业务中随意开展。

## 8. 交付时，应留下哪些可以继续使用的东西？

除了页面，还应留下计量与设备台账、解析配置版本、数据质量说明、告警责任、处理记录和运行维护方法。

验收分开记录：技术链路是否通过，业务流程是否有人使用，观察期结果如何，以及哪些限制尚未解决。

如果第一阶段已经减少抄表和查找记录的工作，可以如实报告这部分效果；后续再依据证据决定是否增加分项计量、扩大区域或引入更复杂分析。

## 9. 用三个问题复盘这个案例

**为什么不能把总表与空调分表相加？**

因为本例中总表已经覆盖空调负荷，相加会重复计量。

**夜间有用电，为什么不直接关闭设备？**

需要先确认使用安排、必要运行条件和授权。

**两个夜间相差 32 度电，为什么不直接称为节能量？**

因为观察差值不自动证明因果，需要比较口径和其他条件的支持。
