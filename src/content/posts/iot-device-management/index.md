A 栋总电表坏了，现场换上一块新表。安装位置没变，网页上的名称也仍然叫“A 栋总表”。

平台可以直接沿用原来的记录，把新读数接在旧曲线后面吗？

如果新表从零开始累计，直接相减就可能产生不合理的结果。新表还可能具有不同的通信地址、数据格式和凭据。

这件小事说明，管理设备不仅是给它起个名字。平台需要分清：实际是哪一台设备，它怎样证明身份，具备什么能力，以及它目前服务哪个业务对象。本篇继续使用假设园区，所有标识均为教学示例。

## 1. 设备名称、身份与位置，是三件事

### 1.1 名称便于人阅读，标识便于系统关联

“A 栋总表”可以作为显示名称，但它可能被修改，也可能在不同园区重复。系统需要稳定、在约定范围内唯一的设备标识。

例如：

```text
设备标识：meter-0081
显示名称：A 栋总表
安装位置：A 栋配电间
业务角色：A 栋总进线计量
制造序列号：设备实物对应的序列号
```

这些字段不必具有相同的生成方式。制造序列号也不能未经确认就当作跨厂商、跨型号绝对唯一的主键。

### 1.2 同一个业务位置，可以先后安装不同设备

换表以后，设备实体改变，但“A 栋总进线计量”这个业务角色仍然存在。

```text
业务位置：A 栋总进线计量
      ├── 原设备 meter-0081：安装日至拆除时刻
      └── 新设备 meter-0142：启用时刻起
```

保留关系的生效时间，就能解释过去的数据来自谁。用户可以按业务位置查看连续历史，计算程序则按实际设备和更换记录处理读数。

这比简单覆盖设备名称更能支持长期使用。

## 2. 标识告诉平台“我是谁”，凭据帮助验证这句话

一条消息写着 `deviceId: meter-0081`，只能说明发送方声称自己是这台设备。平台还需要通过适当的认证方式验证来源，并限制它能做什么。

接入可能使用证书、密钥或其他平台支持的机制。具体方案依赖产品和部署，但至少要区分：

| 信息 | 主要用途 |
| --- | --- |
| 设备标识 | 关联数据与管理记录 |
| 接入凭据 | 验证连接方身份 |
| 权限 | 限定可以上报、查询或执行的操作 |

凭据不应该出现在普通设备列表、公开日志或教学示例里。轮换凭据也不必改变设备业务身份。

如果由网关代设备上报，平台验证的连接方可能是网关，还需要知道它被授权代理哪些设备。不能允许任意网关随意填写另一站点的设备标识。

## 3. 台账回答“这台设备是什么、在哪里、谁负责”

设备台账可以看成管理信息集合，而不是只存序列号的名单。

对于园区电表，至少应围绕实际需要记录：型号与版本、安装位置、所属范围、责任人、安装与维护记录，以及计量范围等。

一个字段是否值得保留，可以看它是否帮助完成某项工作。例如，固件版本有助于确认解析兼容性，责任信息有助于把异常交给正确人员。

反过来，大量没人维护的字段，会让台账显得丰富，却不一定可信。应明确数据从哪里来、谁能修改、变更怎样留痕。

## 4. 物模型回答“它能提供什么数据、接受什么操作”

### 4.1 把能力说清楚，程序才知道怎样使用

可以把物模型理解为面向设备能力的结构化说明。不同平台的名称和格式并不完全一致。

W3C 的 Web of Things Thing Description 使用属性、动作和事件描述交互能力，并包含数据与访问相关描述。这提供了一种理解设备能力的参考，但不代表所有平台都采用同一份模型格式。[W3C WoT Thing Description 1.1](https://www.w3.org/TR/wot-thing-description11/)

在我们的教学模型里，可以写成：

| 类别 | 示例能力 | 要说明什么 |
| --- | --- | --- |
| 属性 | 累计有功电量 | 数值类型、单位、是否只读 |
| 属性 | 最近采集时间 | 时间格式与时间来源 |
| 动作 | 读取当前配置 | 输入、权限、返回结果 |
| 事件 | 采集异常 | 原因、发生时间和相关测点 |

不要因为其他型号支持某个动作，就给全部设备开放同样的操作入口。模型应该表达实际能力，而不是愿望清单。

### 4.2 模型与设备实例需要区分

同一型号的电表可以共享一套能力定义，每一台具体设备则有自己的身份、位置和状态。

这样，新增一台相同设备时，不必重复解释所有字段；但修改共享模型时，也要考虑已经接入的设备与历史数据。

假设某个字段原来单位是 W，后来变成 kW，不能只改显示标签而继续沿用旧解析。应明确版本、迁移或兼容规则，让新旧记录都能被正确理解。

### 4.3 模型与协议映射不是一张表

业务模型可以统一称为“累计有功电量”，不同设备却可能从不同地址读取，并采用不同编码。

```text
设备 A 的地址与编码 ─┐
                    ├→ 标准测量项：累计有功电量，单位 kWh
设备 B 的地址与编码 ─┘
```

协议适配负责把设备原始表达转换为模型表达，业务应用再使用模型数据。分清这两层，才能减少业务程序对具体型号的依赖。

## 5. 一个“在线”状态装不下所有运行情况

假设网关连接正常，但下面一块电表已经十分钟没有有效响应。页面只显示“网关在线”，会让人误以为整组设备都正常。

建议根据用途分别表达：连接状态、最近有效数据时间、设备自身健康状态、当前运行模式和维护状态。

| 状态维度 | 例子 |
| --- | --- |
| 通信 | 上行连接正常 |
| 数据 | 累计电量超过约定时间未更新 |
| 健康 | 设备报告内部异常 |
| 管理 | 正在检修，暂停常规告警 |
| 控制 | 当前处于本地操作模式 |

这些状态可以同时存在。平台应说明状态来源与更新时间，不要把“没有新消息”自动解释成某一种确定的现场故障。

## 6. 从登记到退役，管理的是一段过程

一个示例流程可以是：

```text
登记身份与能力
      ↓
配置接入与权限
      ↓
现场安装、核对与验收
      ↓
运行、维护、配置及版本变更
      ↓
迁移、更换或停用
      ↓
退役并撤销相应接入资格，按规则保留历史
```

登记完成并不意味着现场已安装，第一次连接成功也不等于验收完成。可以通过状态和记录区分这些阶段。

更换设备时，应核对拆除与启用时刻、计量边界、读数衔接和凭据处理。退役后，既要避免旧设备继续以原权限接入，也要保留解释历史数据所需的信息。

## 7. 回到换表：平台应该怎样处理？

对于开头的场景，可以安排以下工作：

1. 记录原设备停用时刻、末次有效读数及更换原因。
2. 为新设备建立或核对身份、模型、解析和接入配置。
3. 记录新设备与业务位置的生效关系及初始读数。
4. 核验现场读数与平台结果，明确更换期间的数据缺口。
5. 按计量规则分段计算，避免把新旧累计读数直接相减。

实际交接可能还涉及更多管理要求，但系统至少应该允许这些事实被记录，而不是只能“删除旧设备、重新添加一个名字”。

## 8. 用三个问题，检查自己是否理解了

**把设备名字改为“A 栋总表”，是否完成了业务关联？**

没有。还需要明确安装位置、计量范围、生效时间等关系。

**知道设备标识，是否就应该允许它上报或接受控制？**

不应该。身份验证和权限需要独立处理。

**两台设备共享同一模型，是否意味着协议地址和编码相同？**

不一定。模型表达能力，协议映射解释具体设备，两者可以分别管理。
