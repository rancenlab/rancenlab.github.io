园区里有一块支持 Modbus 的电表，平台提供 MQTT 接入。项目讨论时，有人问：“这两种协议不同，是不是需要把电表换掉？”

不一定。可以由网关按电表支持的方式读取，再把整理后的数据按平台约定发布。两段通信解决不同的问题，完全可以出现在同一条数据链路里。

这一篇不从报文的每个字节讲起，而是先看两种交流方式：一方提出具体请求，对方给出响应；一方发布消息，由中间服务按订阅关系分发。

下面的设备、地址、主题和数据格式均为教学示例，不能直接作为真实电表的接入配置。

## 1. 先看两段简短对话

第一段发生在网关与电表之间：

```text
网关：请返回约定位置上的累计电量数据。
电表：这是你请求的数据。
网关：按设备资料解释，得到 12,860 kWh。
```

第二段发生在网关与平台之间：

```text
网关：我发布一条 A 栋电表的新记录。
消息服务：把记录转给订阅了对应主题的应用。
数据应用：保存记录。
告警应用：结合规则判断是否需要处理。
```

前者可以帮助理解 Modbus 的请求响应，后者可以帮助理解 MQTT 的发布订阅。类比只描述基本交互，不涵盖全部协议功能。

## 2. Modbus：把问题说清楚，再等设备回答

### 2.1 请求里需要指定做什么、读哪里

Modbus 应用协议定义功能码和数据访问方式。发起请求的一方是客户端，提供响应的一方是服务端；在我们的例子中，网关承担前者，电表承担后者。

它的数据模型包含线圈、离散输入、输入寄存器和保持寄存器。寄存器是 16 位的数据单元，但寄存器对应温度还是电量、如何组合和换算，需要设备资料说明。协议中的地址从零开始，而设备文档或工具界面可能采用不同的表示方式，需要核对。[Modbus 应用协议 V1.1b3](https://www.modbus.org/file/secure/modbusprotocolspecification.pdf)

“寄存器”可以暂时想成有编号的数据格子。它不是显示在网页上的表格，也不保证一个格子刚好装下一项完整的业务数值。

### 2.2 一次读取，要先对照设备的数据说明

假设某台教学设备的文档规定：

| 项目 | 示例约定 |
| --- | --- |
| 测量项 | 累计有功电量 |
| 数据位置 | 从协议地址 100 开始，读取两个保持寄存器 |
| 数据解释 | 两个寄存器组成无符号 32 位整数，高位字在前 |
| 换算方式 | 整数乘以 0.01，单位为 kWh |

采集程序据此生成请求，并解释返回结果：

```text
选择正确设备
      ↓
请求读取指定区域的两个寄存器
      ↓
收到响应，检查结果
      ↓
按设备约定组合得到整数 1,286,000
      ↓
乘以 0.01，得到 12,860.00 kWh
```

如果读错起始地址，可能拿到另一项数据；如果字序或倍率不对，也可能得到看起来像数字、实际没有正确意义的结果。

因此，接入新设备时，不能只测试“有没有响应”，还应选取已知或可核对的现场值，验证解析是否正确。

### 2.3 轮询是在安排一连串读取

当网关依次读取多块电表时，就形成了轮询。例如，读取 A 表，再读取 B 表，然后开始下一轮。

如果某块表没有及时回应，等待与重试会占用时间。采集计划应考虑设备响应、线路能力和异常情况，不能把所有测点都设置为越快越好。

工程上还需要区分：设备返回了明确异常、完全没有响应、响应无法解析。它们对应的排查方向不同，不应都简化成一个“读数为零”。

### 2.4 RTU 与 TCP 是需要明确区分的接入方式

现场经常遇到 Modbus RTU 和 Modbus TCP。前者常用于串行链路，后者用于 TCP/IP 通信；实际接入需要匹配对应封装和连接方式，不能把两者当成完全相同的报文直接转发。Modbus 官方提供应用协议、串行链路及 TCP/IP 的相关规范入口。[Modbus 规范与实现指南](https://www.modbus.org/modbus-specifications)

对于本系列的案例，先选择“网关通过现场串行链路读取电表”这一条路径即可。理解交互和数据解释后，再深入具体帧结构会更容易。

## 3. MQTT：把消息交给服务，再按订阅分发

### 3.1 发布者不用逐个联系使用数据的应用

MQTT 使用发布订阅模式。客户端向服务端发布带有主题的消息，服务端根据订阅关系分发；工程中常把这个服务端称为 Broker。消息体的业务格式需要应用双方约定，协议不会自动知道某个数字代表电量。[OASIS MQTT 5.0 规范](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html)

在我们的示例里，网关发布，存储服务与告警服务分别订阅：

```text
                    ┌→ 数据存储应用
网关 → MQTT Broker ─┤
                    └→ 告警处理应用
```

新增一个有权限的数据使用方时，网关通常不必逐一修改接收方列表，但平台仍需要管理订阅、访问权限和资源承载。

### 3.2 主题像分类地址，消息体才装具体内容

可以为教学系统约定一个主题：

```text
campus/a/meters/meter-a-main/telemetry
```

这只是我们自己设计的命名方式，不是 MQTT 规定的行业格式。

消息体可以采用双方约定的 JSON，例如：

```json
{
  "recordId": "gateway-a-000123",
  "deviceId": "meter-a-main",
  "metric": "active_energy_total",
  "value": 12860.0,
  "unit": "kWh",
  "collectedAt": "2026-10-26T08:00:00+08:00",
  "timeSource": "gateway_read",
  "quality": "read_ok"
}
```

这个例子延续第二篇的信息卡。`read_ok` 只表示示例中本次读取成功，不意味着仪表误差、安装配置和时钟都已经被全面验证。

平台与网关需要共同约定字段含义、必填项、版本和异常表达。不同厂家即便都使用 MQTT，如果主题和消息格式不同，也未必能直接接入同一个业务处理程序。

### 3.3 同一个设备可以同时发布和订阅

设备上报状态时可以作为发布者，接收控制请求时又可以作为订阅者。这两个角色不是固定的设备类别。

但下行控制还需要约定指令标识、参数、权限、有效期和结果反馈。只有通信路径，并不足以说明现场动作已经完成。

## 4. QoS 说明消息交付方式，不替业务确认结果

MQTT 定义三个 QoS 等级：0 为至多一次，可能丢失；1 为至少一次，可能重复；2 通过协议交互实现相应发送方与接收方之间的恰好一次交付。发布端到 Broker、Broker 到订阅端是分别处理的交付过程。[OASIS MQTT 5.0，第 4.3 节](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html)

这些定义有明确的协议范围。即使用了 QoS 2，也不能据此推断数据库写入、业务计算或现场控制天然只执行一次。

考虑这样一段教学流程：

```text
控制应用发布“调整运行计划”请求
      ↓
MQTT 通信完成相应交付
      ↓
设备程序检查权限、参数和运行条件
      ↓
接受或拒绝请求
      ↓
尝试应用新计划
      ↓
返回执行结果，并提供可核查的状态
```

应用收到消息后，可能因为条件不满足而拒绝；也可能接受后执行失败。业务系统需要表达这些差异，而不能在消息发布成功时直接显示“设备已调整”。

对于重复请求，应设计业务层面的去重或幂等处理。所谓幂等，可以先理解为：同一个业务请求再次到达时，不会造成不希望出现的重复效果。具体怎样做到，要结合操作性质和持久化记录设计。

## 5. 让两种协议合作，需要补上中间的解释

假设现场电表已经能够被 Modbus 读取，平台也具备 MQTT 接入。一台网关要把两端接起来，还需要承担这些工作：

| 工作 | 在案例中要完成什么 |
| --- | --- |
| 现场采集 | 正确选择设备、功能与数据地址 |
| 数据解释 | 组合数值，处理单位与倍率 |
| 身份关联 | 把现场设备映射为平台设备标识 |
| 时间与质量 | 说明读取时间及异常状态 |
| 上行发布 | 按约定主题与消息格式发送 |
| 异常恢复 | 根据设计缓存、补发并保留排查记录 |

这解释了为什么“协议转换”往往不只是更换报文外壳。

如果只是把电表返回的原始字节放进 MQTT 消息，平台虽然收到了消息，仍需要另一个程序解释它。这可以是一种设计选择，但解释职责必须有明确归属。

## 6. 三种现象，分别应该查哪里？

### 6.1 电表有响应，但电量明显不对

先核对测量项、起始地址、数据类型、字序、倍率和现场参考读数。此时通信成功是一条有用证据，却不是解析正确的证明。

### 6.2 网关发布成功，但报表没有新记录

应沿着 Broker、订阅关系、访问权限、消息格式校验、业务处理和存储逐步检查。发布调用返回成功能证明到哪一步，需要结合客户端实现与交付设置判断。

不要因为现场电表仍在线，就排除上行或平台处理问题。

### 6.3 指令消息已收到，但设备状态没有变化

先查看设备是否接受请求，以及拒绝原因或执行结果。还需要检查参数、有效期、现场控制模式和运行条件。

反复重发之前，应确认操作是否允许重复，以及能否通过同一个业务指令标识追踪处理状态。否则可能把一次失败排查变成多次不明确的操作。

## 7. 用三个问题，检查自己是否理解了

**电表支持 Modbus、平台支持 MQTT，是否必须更换电表？**

不一定。具备相应能力的网关可以承担采集、解释和发布，前提是接口、协议与数据定义都得到正确配置。

**两台设备都使用 MQTT，就能自动进入同一个平台的数据模型吗？**

不能直接这样推断。主题、身份、消息格式、单位和权限等仍需要匹配。

**MQTT 消息交付完成，是否意味着水泵已经启动？**

不意味着。通信交付、程序接受、现场执行和状态反馈，是需要分别确认的环节。
