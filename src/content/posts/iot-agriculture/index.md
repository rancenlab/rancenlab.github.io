田间平台显示某个土壤测点的含水量正在下降。系统是否应该立刻打开阀门？

还需要知道测点埋在哪里、对应什么土壤、种植什么作物、处于哪个阶段，以及近期是否灌溉或降雨。同一个数值，在不同条件下可能意味着不同的事情。

物联网能够让农业现场更容易被持续观察，但生产判断仍需要农艺知识与实际条件。本篇使用假设种植区说明系统设计，不提供通用灌溉阈值或作物操作处方。

## 1. 先把田块当作有差异的现场

一片地并不一定处处相同。土壤、地形、排水和灌溉设施差异，都可能导致不同位置的水分变化不同。

只在入口附近装一个探头，就把它代表整块田，可能导致局部已经湿润，其他位置却仍未得到适当灌溉。

因此，要先明确管理单元：哪些区域具有相近条件，可以怎样分区观察和操作。测点应与田块、深度、安装位置、作物和有效时间关联。

```text
种植地块与管理分区
          ↓
具有代表性的测点和安装深度
          ↓
土壤、环境与设施数据
          ↓
结合农艺要求形成安排
```

USDA ARS 关于土壤水分传感器应用的资料指出，正确安装、校准和维护，对基于传感器的灌溉安排很重要。[USDA ARS：土壤水分传感器与灌溉](https://www.ars.usda.gov/research/publications/publication/?seqNo115=336401)

## 2. 需要的数据，不只是一个“湿度值”

不同仪器可能测量土壤含水量、土壤水势或其他量，不能因为中文界面都简称“湿度”就直接比较。

记录应保留测量项、单位、仪器与解释方式。空气相对湿度和土壤含水量，也不能混为同一类数据。

| 信息 | 可以支撑什么判断 |
| --- | --- |
| 土壤相关测量 | 观察测点处水分状态及变化 |
| 气象与降雨记录 | 理解环境变化及已发生的降水 |
| 作物与生长阶段 | 确认当前管理目标和适用要求 |
| 灌溉记录 | 解释何时、何地采取了什么操作 |
| 流量、压力与设备状态 | 核对水是否按预期输送 |

天气预报可以作为安排的依据之一，但它不是已经发生的降雨。系统应区分预测与实测，避免把预计补水量直接记作田间实际得到的水量。

## 3. 从“看到变化”到“安排灌溉”

### 3.1 一次读数不如一段变化容易解释

观察灌溉前后、降雨前后及不同深度的变化，能够帮助理解测点表现。若某个探头长期不变，还需要检查是否确实稳定，还是安装、供电或通信出现问题。

不能因为平台连续收到相同数字，就认定数据可靠；也不能遇到一个跳变，就自动判断田间水分突然变化。

### 3.2 先形成建议，再明确执行条件

可以为教学场景安排以下过程：

```text
检查测点数据是否有效
          ↓
结合土壤、作物阶段与近期操作
          ↓
参考天气及现场可用条件
          ↓
由管理人员或经过验证的规则形成计划
          ↓
检查水源、泵阀和允许操作条件
          ↓
执行并核对结果
```

对于新接入的田块，先让建议与实际观察相互核对，比直接把未经验证的阈值接到阀门上更容易发现误差。

### 3.3 不要把别处的阈值当作自己的答案

不同土壤和作物条件，需要不同解释。官方农业指导也强调，应结合具体田块和作物逐步理解读数及灌溉后的变化。[安大略省：用土壤水分监测改善灌溉决策](https://www.ontario.ca/page/monitoring-soil-moisture-improve-irrigation-decisions)

系统可以提供规则配置与历史分析，但规则来源、适用区域和修订记录应明确，不能让一个默认值悄悄控制全部地块。

## 4. 发出开阀指令，不等于田里已经得到水

泵未启动、管路堵塞、阀门故障或水源不足，都可能让计划无法按预期执行。

因此，可以把核验分成几层：

| 层次 | 要确认什么 |
| --- | --- |
| 请求 | 对应操作是否被接收与接受 |
| 设备 | 泵阀是否进入预期状态 |
| 输送 | 流量、压力等是否符合现场预期 |
| 田间 | 相关区域是否出现合理的后续变化 |

土壤测点对灌溉的响应可能存在时间与空间差异，不能要求每次开阀后所有探头立即上升。核验方法应结合设施和农艺条件确定。

操作记录应包含区域、时间、持续过程和异常情况。如果具备有效计量，可以记录实际水量，而不是仅用计划时长代替实际用水。

## 5. 断网和无人值守，要提前说明怎么处理

田间设备可能受到供电、覆盖、环境和维护条件影响。平台离线时，应明确哪些本地任务继续，哪些操作暂停，以及人员怎样发现故障。

已经过期的开阀请求，不宜在网络恢复后无条件执行。持续动作也需要停止条件和本地处置能力，不能只依赖云端之后再发送一条关闭指令。

设备防护、安装固定、供电维护和探头检查，也都是系统的一部分。软件界面做得完整，不会免除这些现场工作。

## 6. 农业应用还可以支撑哪些工作？

除了灌溉，设施农业可以结合环境、设备和使用计划辅助管理通风、遮阳等设施；农机与资产监测可以辅助了解位置、工作状态和维护需求；生产记录可以关联地块、批次与操作。

这些能力需要各自的专业条件。环境数据能提供线索，却不能单独完成所有病害诊断；远程看见设备，也不代表平台有权任意改变生产过程。

可复用的是设备接入、身份、时间、数据质量和流程记录，具体判断与动作仍需要面向对象设计。

## 7. 怎样衡量是否有帮助？

可以同时记录用水、能源、人工巡查、故障处理和生产表现。

减少用水不一定单独代表改善，还需要确认作物需求和生产目标得到满足。反过来，天气更干燥或种植结构变化时，用水增加也不能直接归因于系统失效。

评价应明确地块、面积、作物、生长阶段、天气和时间范围。短期试点先确认记录与操作可靠，再逐步积累能够比较的结果，不宜把一次试验当作长期收益保证。

## 8. 用三个问题，检查自己是否理解了

**一个测点含水量下降，是否说明整块地都需要立刻灌溉？**

不一定。要看测点代表性、土壤、作物与其他条件。

**阀门回复开启成功，是否可以直接认定灌溉完成？**

不能。需要核对输送与实际过程，必要时观察田间反馈。

**其他地块用得好的阈值，能否直接复制？**

不能直接认定适用。需要确认条件，并通过现场记录验证和调整。
